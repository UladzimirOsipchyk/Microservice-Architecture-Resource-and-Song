**e2e Tests:**

✔ Resource Service is not just a basic CRUD app — it involves external systems, file I/O, binary data, and cross-service communication. Here's why E2E tests are crucial:
 - MinIO / S3
Uploading MP3 files to object storage, Generating and retrieving file URLs, Downloading files to serve as audio bytes.
E2E tests validate that integration with MinIO/S3 works — e.g., correct file is stored and returned.

- Binary File Upload & Download
Uploading MP3s as raw byte[] via HTTP. Returning audio bytes in GET /resources/{id}.
E2E tests ensure that binary data flows correctly from the client through to storage and back.

- PostgreSQL Persistence
Resource metadata (like file name and URL) is stored in PostgreSQL. The schema is automatically updated, and SQL is generated by JPA. E2E tests catch schema mismatches or missing tables — especially important when using auto-DDL.

- Multiple Layers of Logic
You have a controller → service → repository → S3 interaction chain. E2E tests ensure all layers behave correctly together.
E2E validates the full logic, wiring, and serialization/deserialization.

- Message Processing

- Real HTTP Behavior
You rely on request headers (like Content-Type) to determine file format.
Response structure (e.g., ResourceDTO) needs to match client expectations.
E2E tests validate that the real HTTP contract is honored, avoiding client-side surprises.

**Component Tests:**

✔ Component tests verify one service in isolation by interacting with its external dependencies, such as:

 - Databases (e.g., PostgreSQL, MongoDB)
 - Messaging systems (e.g., RabbitMQ)
 - External HTTP APIs (e.g., calling Song Service from Resource Processor)

This is different from unit tests (mock everything) and integration tests (multiple services tested together).


**Contract Tests:**

✔ Song Service is the best candidate for contract tests because:
 - It exposes APIs that clients rely on.
 - It interacts with Resource Processor, making API stability crucial.
 - It can use message contracts if handling asynchronous events.

✔ Why Contract Tests Belong to the Controller Layer
 - They test the API contract
Contract tests validate how external clients (other microservices or frontend apps) interact with your API.

 - Since the controller layer exposes the API, contract tests focus on HTTP request/response validation.
 - They ensure API stability
If a controller changes its request/response format, contract tests will fail.
This prevents breaking changes for API consumers.
 - They verify serialization & deserialization
The controller layer handles JSON serialization (output) and deserialization (input).
Contract tests ensure the correct HTTP status codes, headers, and response body format.
